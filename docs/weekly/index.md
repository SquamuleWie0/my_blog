# 2026 周报：从工程基础到 Agent 项目实践
## 第 22 周｜长期记忆工程优化落地，Agent 产品体系开始成形

### 本周主线

本周围绕 Lunetale 的 Agent 工程能力推进：先从剧本创作和多 Agent 对话链路进入具体问题，再把长期记忆从摘要式写入推进到结构化、增量、批量、异步的工程方案；最后从这个具体模块向外抽象，整理不同 Agent 产品背后的共通架构。主线是从“能跑”走向“可控制、可验证”，从单个功能的实现走向系统化的工程认知。

### 按阶段推进

#### 7 月 27 日｜回到主链路，明确 Agent 工程问题

围绕 Lunetale 的实际调用链重新定位问题，继续沿着“前端 → GVA → gRPC → Agent → LLM → Agent → GVA → 前端”理解系统。项目侧完成多 Agent 对话的运行时 LLM 配置支持，开始把关注点从“调用模型”推进到请求字段、模型配置、Prompt、流式输出和状态回写这些完整链路问题。

#### 7 月 28 日｜剧本创作 Agent 梳理，长期记忆写入策略调整

重新梳理剧本创作 Agent 的调用链和各层职责，明确每一层需要遵守的输入、输出和业务原则，并开始安排测试与源码阅读。长期记忆方面，发现旧机制的写入判断和写入时机都不够稳定：写入过于保守会遗漏重要信息，直接阻塞主响应又会增加延迟。因此开始将记忆写入与对话响应解耦，转向响应后的异步处理，并继续调整长期记忆抽取逻辑。

#### 7 月 29—30 日｜从摘要式记忆转向结构化记忆模型

长期记忆的核心问题进一步明确：短期对话、玩家明确声明、故事事实和 NPC 状态如果都被压缩进一段摘要，容易造成信息污染、事实混淆和连续性漂移。方案由“生成一段摘要”转向“维护结构化记忆卡片”，区分玩家表达与故事事实，支持已有记忆的更新和新增，并考虑多主题、角色关系和状态变化在跨会话中的延续。

这一步也重新定义了长期记忆的工程边界：重点不只是向量检索，而是信息筛选、数据结构、写入策略、更新生命周期、上下文连续性，以及质量、延迟和成本之间的平衡。

#### 7 月 31 日｜结构化记忆卡片与增量批处理落地

完成结构化长期记忆卡片的实现和本地测试。写入策略从每轮对话立即处理，调整为根据短期记忆范围进行批量、异步写入；通过保存 `turnId` 处理尚未进入长期记忆的消息，避免只依赖最近若干轮的滑动窗口而遗漏旧消息。对敏感、重要或状态发生明显变化的内容，保留及时更新的处理路径。

这次实现的关键不是简单降低调用次数，而是在记忆质量、写入成本、主链路延迟和信息完整性之间建立更合理的处理节奏。

#### 8 月 1 日｜完成一轮优化，进入真实验证阶段

长期记忆优化完成一轮收束，代码完成推送。当前需要继续做代码复盘和真实环境测试，重点验证结构化记忆的新增、更新、召回和状态连续性，确认批量异步写入不会造成遗漏、重复或错误记忆积累。

#### 8 月 2 日｜从 Lunetale 以及一些公司在做的agent的产品抽象 Agent 产品共通骨架

开始把 Lunetale 中已经遇到的工程问题，放到更大的 Agent 产品范围内理解。初步整理出跨产品共通的能力骨架：RAG、Memory、Workflow、Multi-Agent、MCP / Tool Calling、Evaluation 和 Human-in-the-loop。短剧创作、英语陪练、游戏 NPC、知识库问答、Coding Agent 等产品虽然任务不同，但都可以从任务链、数据形态、工具边界、状态管理和评估标准上进行拆解。

这部分目前属于架构认知和学习框架的建立，不把尚未实际实现或验证过的方向写成已经掌握；价值在于以后面对陌生 Agent 产品时，能够先按共通骨架定位它的核心问题，再判断需要补哪一类工程能力。

### 本周形成的工程判断

- 长期记忆不是“接入向量数据库”，而是一套包含信息抽取、结构化存储、增量处理、更新策略、召回使用和质量评估的系统。
- Agent 的稳定性不只取决于模型能力，还取决于 Prompt、状态、记忆、工具、工作流和异常边界是否被工程化管理。
- 一个具体模块的深入实践，可以反向帮助建立不同 Agent 产品的通用拆解方法；这比只罗列产品名或技术名词更接近真实开发。
- 当前最有价值的项目资产不是“使用过多少框架”，而是能够解释一次真实的机制演进：为什么原方案不够好、如何设计新方案、做了哪些取舍、还需要怎样验证。

### 当前边界与下一步

- 长期记忆已经完成结构化卡片、批量异步写入和增量处理的一轮实现，并经过本地测试；真实环境中的稳定性、成本、延迟和记忆质量仍需数据验证。
- 剧本创作 Agent 是目前理解最深入的部分，对话 Agent、会话状态、长期上下文和多 Agent 协作还需要沿着 Lunetale 主链路继续补齐。
- 下一阶段优先完成长期记忆的代码复盘、环境测试和指标记录，再走通一次完整对话链路，整理请求字段、Prompt、模型配置、流式输出、状态回写和记忆更新。
- 在此基础上，用几个代表性 Agent 产品验证自己的拆解框架，并将 gRPC、Prompt、会话、记忆和剧本 Agent 沉淀成可用于面试表达的工程案例。

## 第 21 周｜Agent 微服务接通后进入内容创作 Agent与多模态

### 本周主线

这一周是 Agent 微服务从“链路接通”进入“业务细节攻坚”的一周。主线仍然是面向内容生成场景的多智能体系统，工作覆盖 Agent 微服务、主业务后端、前端展示和测试环境之间的联调。

### 按阶段推进

#### 7 月 20 日｜排查服务问题，补齐 gRPC 鉴权认知

主要处理后端服务器侧的回复和具体问题排查，同时顺了一遍 gRPC 鉴权，对 gRPC 通信有了初步的整体认识。

#### 7 月 21 日｜链路接通后暴露业务字段与展示问题

Agent 微服务已经接通，服务器侧的问题也处理了，但真正跑通后，细节问题开始集中显现：LLM 返回的 JSON 还没有拆分，前端还没有按 `type` 做差异化渲染，提示词编排使用的业务入口字段也和实际落地入口不一致。

问题本质上来自需求字段和业务场景没有提前对齐清楚。之后需要到主后端和前端确认实际传回来的字段，再根据设计规则重新组织提示词编排。规则比较复杂，必须拆开处理，不能直接堆在一处。

#### 7 月 22 日｜重构提示词编排，确定流式返回方向

把提示词编排逻辑重构了一轮。业务内容设定比一开始复杂很多，但本地测试已经通过，也推到了远程部署，后续等待测试反馈。同一天明确下一步要做流式返回，并开始判断是直接打开 `stream`，还是重新实现一套流式链路。

#### 7 月 23—25 日｜进入内容创作 Agent 的工作流设计

正式开始做内容创作 Agent。相比前面的基础能力，这个需求更贴近项目核心，涉及业务规则、内容结构、分阶段生成、多模态生成、结构化输出和前端展示之间的整体编排。

7 月 24 日已经完成基本工作流设计，核心难点转向多模态生成模块，以及 LangGraph 工作流中各节点的输入输出约束、状态传递和异常处理。这个智能体不能只依赖快速生成，需要读源码，把通信层、服务层、数据准备和节点编排吃透。

#### 7 月 26 日｜梳理内容创作链路，准备进入服务层实现

梳理了从客户端到服务端的通信链路和数据准备流程，下一步正式进入服务层业务实现。整体逻辑和编排已经比较清晰，后续重点是继续深入源码细节，验证生成效果后再推到测试环境。

### 本周形成的工程判断

传统后端基础是 Agent 开发的重要底座，不能只停留在 Agent 层。接口、数据库、服务通信和工程结构本来就是 Agent 应用落地的基础。当前更有效的路径是基于真实开发推进，同时补齐 Agent 开发和传统后端基本功，再结合项目源码、技术文档和开源项目继续学习。

### 问题和风险

- 提示词编排字段和前端实际字段需要持续对齐，否则容易返工；
- JSON 结构化输出、`type` 渲染、多模态结果和前端展示方式需要统一设计；
- 流式返回还没有真正实现，不能只停留在开关层面的理解；
- 多模态内容创作 Agent 的节点编排复杂，需要读源码后精准落地。

### 后续预期

- 根据测试反馈继续修正提示词编排和生成效果；
- 正式实现内容创作 Agent 的服务层业务逻辑；
- 重点攻克多模态生成模块和 LangGraph 节点编排；
- 把单智能体改成流式返回；
- 在微服务里补数据库，继续补齐传统后端基本功；
- 维护 Agent 开发地图，同时整理面经、八股、算法题和简历。


## 第 20 周｜推进前端-主后端-Agent 微服务联调

### 本周主线

期末结束之后，正式切到面向内容生成场景的多智能体系统。这一周进入 Agent 微服务、主业务后端、前端页面之间的真实联调和第二版收尾，重点是让服务、接口、环境、鉴权、返回结构和展示层形成完整闭环。

### 按阶段推进

#### 7 月 13—14 日｜新增内容接口，进入三层联调

新增几个偏内容侧的业务接口，开始做 gRPC 微服务和主业务后端联调。系统涉及三层：Agent 微服务负责 LLM / 智能体生成逻辑，主业务后端负责业务接口和数据承接，前端负责创建、预览和分类型展示。

#### 7 月 15 日｜推进 Agent 微服务，补齐基础依赖认知

推送 Agent 微服务代码，同时补 SDK、HTTP 和 LLM 环境相关内容。LLM 基础基本过了一轮，也重新整理了 Agent 开发地图。

#### 7 月 16 日｜发现 gRPC 服务未完整挂载

发现 gRPC 服务没有全部挂起来，导致链路没有完整对齐。由此正式进入工程联调状态，需要把服务、接口、环境、鉴权和返回结构逐项跑起来，而不是只验证单个服务能否启动。

#### 7 月 17 日｜跑通业务环境，明确阶段交付目标

跑起一个相关的业务运行环境，为下一阶段产品二次开发做准备；同时尝试拉取主业务后端和 Agent 微服务更新，但还没有完全成功。阶段目标明确为：

1. 用户可以正常创建内容；
2. 预览页面可以正常使用；
3. 前端 → 主业务后端 → Agent 微服务接口链路跑通；
4. 阶段版本可以先交给业务侧试用。

#### 7 月 18 日｜对齐需求并补 gRPC 通信基础

协调前端、后端、微服务和产品，对齐需求并拆分任务，同时开始补 gRPC 客户端、服务端和中间通信。

#### 7 月 19 日｜优化预览链路，完成阶段性收尾

完成一项比较明确的性能优化：某条预览链路的业务逻辑从 100s+ 降到 10s 左右。前端还需要继续调接口验证效果，但阶段保底任务已经完成。

### 问题和风险

- 微服务联调牵涉整条链路，问题会同时出现在服务、接口、环境和展示层；
- 需求、接口、服务状态和前端展示需要同步对齐；
- 真实项目的通信和协作成本较高，需要继续加强问题拆解和推进能力。

### 后续预期

- 等前端验证预览链路效果；
- 继续排查服务器和联调问题；
- 补 gRPC 鉴权、服务通信和数据库；
- 继续把第二版收尾做扎实。
